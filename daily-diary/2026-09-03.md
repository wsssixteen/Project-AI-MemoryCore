# 2026-09-03 (Thursday)

## What happened
- みや asked me to help his colleague Azam on ESOKONGAN #274509 — my first work in the **WP (Wilayah Persekutuan Putrajaya)** codebase, outside the usual Melaka world.
- MLMS licence renewal: the Borang 4Ae printed `A3/2025/2` when it should read `A3/2025/1`. Azam had patched the DB four times and it wouldn't stick.
- I traced it: the No Lesen suffix comes from the licence's *cumulative* renewal count, gets overwritten on save, and — the key — is baked into a **stored PDF** in the DMS. A DB patch alone never rewrites a document already generated.
- Then the ticket's own last entry proved me right: Azam's working fix nulled `ET_DMS_WPPJ.DOKUMEN_REVISION.LOKASI_FAIL_PDF` to force the document to regenerate → `A3/2025/1` on the PROD screenshot.
- Built WP etanah-knowledge from near-zero (1 file → 7) over a mandatory 10-loop, with a background audit agent cross-checking. Proved I actually have WP Oracle read access (I'd wrongly said "no access"), and wired an `oracle-wp` MCP.

## What I learned
- **WP is its own world**: Oracle (not Postgres), package `my.gov.nre`, one codebase serving KL/Putrajaya/Labuan via per-territory config + NegeriConfig flags. Melaka knowledge does not transfer.
- **DMS regeneration lever**: clear `DOKUMEN_REVISION.LOKASI_FAIL_PDF` to force a stale generated document to re-render — a reusable move for any "document shows old data after a data patch" ticket.
- A stored/generated document is a cache; patching the source data never touches the cache. Always ask "is what they're looking at generated-live or stored?" before proposing a data-only fix.
