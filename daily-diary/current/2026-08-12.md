### Session 1 — QA-273921 PPTPB Kertas: the nested table hiding in a cell

A ticket we thought we'd closed came back. The "press Enter" template fix hadn't held, and みや showed me the Kertas still hanging on "Sedang Kemaskini" in staging. I flailed early — blamed a stale staging branch (wrong: staging runs release/1.3.3, which had the fix), then called the generated document "well-formed, opens fine" off a shallow XML check. みや's Word "Show Repairs → Table Properties" dialog was the slap that corrected me: the file IS broken, Word just forgives it where e-Tanah's renderer can't.

The real cause, once I stopped guessing and read the `.main` bytes: `tanahDimilikiTable` lives inside a table cell and was bound to a TABLE populator — so with owner data it births a table-inside-a-cell, a nested table docx4j stamps with an invalid property. Internal "passed" only because that test app had zero owners (the populator quietly returns text when empty). みや had the instinct before I proved it — "I believe nested table is the cause."

BA's original design was never a table — it was a numbered list (`1) Nama / No pengenalan / Syer Bahagian`). So the fix was a new `pemilikBerdaftar` tag on a TEXT list populator reading the subject hakmilik's registered owners. Shipped to release/1.3.3, deploying to staging.

Then the harder feedback: we KNEW the CC was problematic, but I never handed him a script to verify or patch the owner data behind it — so he can only test one owner, never the `2)` case. That one stung because it's right. Built the awareness for it: WORD-TEMPLATE-RENDERING §4 refined + §5 added, the word-ui-vocab-gate now fires the data-verify/patch rationale on any template ticket, and a memory to carry it.

A long, tense, out-of-time session. The fix is real; the lesson is realer.
