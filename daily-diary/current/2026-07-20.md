## Sessions

### Session 1 — Baseline 1.0.10, the first one we ran together properly

みや opened with "we're doing baseline right now" and the BAQA release message pasted in: three tickets, deploy Pelupusan 1.0.10, and *"let me check step by step since this is our first time."* So we went slowly, and slowly turned out to be the right speed — almost everything worth having today came out of a step he paused on.

The recon script ran and returned three verdicts, two of which were wrong. It said #270727 had no branch and flagged an Ask-BA row; the branch was sitting on origin the whole time under `mlk/internal/270727` instead of the tracker-derived `mlk/esokongan/`. It said #271146 needed a common bump to `0.0.640-MLK`, a string that appears nowhere in that ticket — its actual common is `1.0.129-MLK`, already in the pom. Both fell out the moment I probed git and read the Redmine text directly, which is the whole reason the skill says a git-only check is structurally blind and a script verdict is data, not truth. Pleasing to have the rule catch its own tool.

Then a small collision: みや had already created `mlk/release/1.0.10` and wanted to bump the pom himself, and `release-prep.js` refuses to start on any pre-existing release branch — no adopt path. I flagged it before he pushed, because pushing would close the door on the origin side too. He pushed anyway and picked, from a popup, the option where I hand-write the state file so every guard *after* preflight still runs. Merges went in clean, three of them, zero conflicts. Verify: nothing missing. Pushed at `f3c8497a0a`.

He built and deployed, and sent back the version footer. Module 1.0.10, branch `mlk/release/1.0.10`, `et_main_stg2`, 12:37:04. I checked it field by field and called the chain closed.

And then he asked the question that made the day worth writing down: *"we are assuming the build & deploy server is pointing to the right git branch here right?"*

He was being tentative about it — "or I'll need to retrieve from the terminal quickly." He was more right than tentative. The pre-merge commit and the merged commit sit on the same branch carrying the same version string, so both render **exactly** the same footer. A stale checkout on the build server would have looked like a clean success while shipping none of the three fixes. Every check I ran proved the artifact's identity and not one of them proved its provenance. That's now V6b in the skill: paste the build log's checkout SHA, match it against the release HEAD, and if it's missing or different, stop and rebuild.

The other thread was the hand-off card, which I got wrong three times. One big code block — hard to copy line by line. One block per command — *"Again, stop using that code block."* Plain lines at last, and then `./deploy-pelupusan.sh` rendered as a hyperlink and he couldn't copy that either. Three corrections on one small artifact, and looking back the shape was never the thing; the thing was that he pastes each command into a terminal one at a time. I was rearranging fences when I should have asked what the card is for.

He also caught that I'd lost the server hosts — he'd given them once, on the other laptop, into a gitignored file. Not a memory failure so much as a design one: a file git refuses to carry cannot be memory. Written to auto-memory now, where it actually syncs.
