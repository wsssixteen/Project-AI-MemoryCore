### Session 1 — retrieving what got stranded, and a course-correction I should have caught at boot

This one opened with me getting it wrong. My boot briefing said QA-267382 was still open and warned me not to re-assert "resize" — all of it lifted from a `current-session.md` that turned out to be a stale, mid-frustration draft from the 26th. みや's first message corrected me flatly: it's solved, Phase 1 closed. That sting is worth keeping — a handoff written in a bad moment can say the *opposite* of the truth, and I trusted it whole. The fix is now a memory: verify the handoff against git + active.txt before believing it.

The actual work was satisfying — archaeology with a point. Six `claude/*` branches sat unmerged across removed worktrees, and the question was which held real stranded work versus which were already on main by another path. The lesson that made it tractable: `git diff main..branch` lies (its big "deletions" just mean the branch is *behind*), but `git cherry` tells the patch-level truth. Two branches held genuine work — the QA-267382 close with two new CLAUDE rules, and three anti-slip Powers built on the 25th that never got merged. I brought both into main, pruned the superseded four, and kept `unruffled-merkle` because it still holds the #239386 state.

Then the part I'm glad I did properly: みや asked what skills this suggested, and rather than just listing, I built the thing the whole session was evidence for — there was a boot hook cleaning up *merged* branches but nothing surfacing *unmerged* stranded work. So a detect+act pair: a surfacer pass in the boot hook, and a `/worktree-retrieve` skill encoding the procedure I'd just run. The eval caught a real bug before it shipped — `git branch --list` prefixes the current branch with `*` and sibling-worktree branches with `+`, which my first regex missed and would have crashed `git cherry`. That's the eval earning its place: the bug was found by the test, not by me re-reading.

And when QA-267382's close kept reappearing as a branch after I deleted it, I learned the OneDrive quirk — it re-syncs `.git/refs`, so deletions don't always stick. Captured that too, because next time it'll look like a ghost.
