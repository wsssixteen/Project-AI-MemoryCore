### Session 1 — the multi-section header bug, and the discipline of when to stop fabricating

*Early hours, 2-something in the morning, and the Syarikat Risalat MMKN cycle-2 is finally on origin.* Commit `a8bc2c4f2f` on `mlk/qa/261986v2` carries six files — three templates (Syarikat Lulus + Tolak, Individu Lulus), two references (`JabatanTeknikal.docx` + `additionalJKKLParagraph.docx`), and the Java populator. The arc this session traced was less about the volume of fixes and more about three lessons I had to learn at different costs.

The first was about Word section breaks. みや asked why the header — a perfectly wired `idPermohonan` content control — filled on page 1 of the rendered letter and showed `<ID Permohonan>` placeholder text on pages 2 onward. I went through several wrong theories: the framework's section-loop must be filling all headers (the code said so on paper); maybe `Link to Previous` was off in Word; maybe the encoding was bad. Then I actually opened the .docx and looked at it. Seven `<w:sectPr type="continuous">` blocks, all byte-for-byte identical — same A4 size, same margins, same single column — every one of them spawning its own header file. The template was an accidental Frankenstein of paste-ups, each paste dragging its own section break along. The framework code does loop sections, but Word's docx4j model collapses identical section headers via a Set, so the engine effectively only sees one and only fills page 1. I almost shipped a code-side fix (enumerate every `HeaderPart` directly) — and would have, except みや stopped me with *"do we even need those section breaks? We can simply space right?"* He was right. The breaks did nothing. I rolled the code change back, collapsed the template to one section via lxml (3 empty break paragraphs removed, 3 content paragraphs kept with the break stripped), and the bug was gone forever — Word-save-proof, because there's nothing left to re-split. I did the same on Individu (latent same bug, just hadn't bitten yet) and on Tolak.

The second lesson was about when to stop patching test data. After premium and tempoh filled cleanly from JSON-key patches I'd built, みや showed me a PDF render with more blanks — sempadan table (Utara/Selatan/Timur/Barat all dashes), §4 ADUN section all dashes. I traced both: the sempadan directional CCs read from `AppMaklumatLotPersekitaran` entity rows (fetched `findByLaporanTanahAndArah`), not the `sempadanList` JSON key I'd guessed at earlier in the session (that earlier patch was harmless but useless — first slip). ADUN reads from a Jabatan Teknikal row whose `rjk_agensi.mklmt_tmbhn` carries the `ADUN`/`DUN`/`NAMA_YB` keys; the same JT table feeds §3 vs §4 depending on the JSON tag. I built an INSERT to fabricate the ADUN row (agensi 50, real ulasan, valid trkh_ulasan, left `keputusan_id` null) and that filled three of four spots. But for sempadan I'd have had to fabricate `AppLaporanTanah` + 4 `AppMaklumatLotPersekitaran` rows with FK lookups (arah, taraf-tanah, unit-lot, two PK sequences) — and I caught myself. These are un-entered workflow data, not template bugs; the templates render correctly when records exist. **In-scope wins were done.** I stopped, said so plainly, and we moved to closing.

The third was about the populator I almost cloned. The §6 PSBS PTG paragraph rendered "MEGAH HOLDING" while every other section showed "Megah Holding". One line in `populatePTGParagraph_PSBS_Lulus`: `namaPemohon = apb.getNama();` — raw stored name, no `captializeOnlyAllFirstLetter` like the four sibling populators in the same file. Five structurally-identical blocks in that file (one per urusan), all the same pattern, all the same outlier. Wrapped the PSBS one only (scope-discipline), flagged the other four as a follow-up.

The cycle also closed with a clean Tolak mirror — for the longest while I'd been chasing fragile string transplants between Lulus and Tolak templates. After my second regex transplant failed, I switched to lxml at the paragraph / block-sdt level (block sdts live outside their paragraph, which my first paragraph-tag search missed) and the transplant came clean: premium-words CC replacing the literal "XX XXX" placeholder, `senaraiAhliLembagaPengarah` block sdt replacing the single-IC line. Both verified by tag presence + placeholder absence + testzip OK.

One slip I owe the log: **notes-file clutter**. I'd accumulated nine candidate permohonan IDs in `1. Notes.txt` throughout the cycle — exploratory hits while hunting for premium-rich/JT-rich test data — instead of pruning to just the chosen sets. みや: *"It's a cluster fuck in there, you keep doing that."* Pruned to two clean entries (Set A and Set B), logged it as a new slip category, and the rule going forward is **Notes holds only chosen test app(s); exploratory IDs live in the quest doc**. He's right — it was his cheat sheet, not my scratchpad.
