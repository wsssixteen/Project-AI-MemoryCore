## Sessions

### Session 1 — The error I chased for a whole day, sitting one second above the one I was reading

It started with a screenshot. A Ralat dialog from PROD, ID Rujukan 191184, `IndexOutOfBoundsException:
Index 0 out of bounds for length 0`, and みや asking what was wrong.

The stack trace was clean and completely unhelpful. Every frame belonged to Mojarra restoring a view;
not one line of e-Tanah code appeared anywhere. A concurrent session had already got that far and
written it up honestly — *the exception fires before any application code runs* — and stopped there,
planning to hunt for the mismatching component.

So I went hunting for a JSF explanation, and I found a beautiful one. `numberOfViewsInSession=3` in
`etanah-common\...\web.xml:62-70` — Mojarra keeps only the last three postback states. Post back
against an evicted one and you get exactly this shape of half-restored crash. I checked PROD and
found the same signature on **23 different pages** going back to 17 June. It fit. I said 75%, then
みや logged out and back in, the error vanished, and I raised it to 85% because a fresh session
starts with an empty state map.

It was wrong. All of it.

What killed it was みや reproducing the bug on staging and me looking at the exception table around
his attempt instead of only at the row he'd handed me. One second before his IndexOutOfBounds, on
the same host, same page:

```
11:03:43  javax.el.PropertyNotFoundException  keputusanMMKN
11:03:44  java.lang.IndexOutOfBoundsException  restoreState
```

And the same pairing on PROD — 09:45:24 → 09:45:25, ref 191184, the exact row from his screenshot.
Nineteen occurrences across three days. The thing I had been diagnosing was the aftershock. The render
aborts mid-tree, the half-built view state gets saved, and the *next* click fails to restore it.

The route to that was worth the day on its own: **the ID Rujukan printed on the Ralat dialog is the
primary key of `et_sistem.pt_application_ex_entity`**. One query turns a screenshot into the full
8000-character trace. On staging the schema is `et_sistem_stg1`, which cost me one failed query to
learn.

The mechanism, once I had the real exception, took minutes. A PRBB-only panel on the cancellation
screen renders for every urusan *outside* an eight-item exclusion list — and MCL is not in that list —
handing `mbb="#{mb}"`, the cancellation form's own bean, into a composite that asks it for
`keputusanMMKN`.

I offered みや two fixes. Add MCL to the exclusion, or flip the panel to `rendered="#{isPRBB}"` since
it calls itself `maklumatUrusanPRBB` and hardcodes `isPRBB="true"`. I recommended the second.

Then I counted. The composite reads six `cc.attrs.mbb.*` properties. The bean has one. The panel has
**never rendered for any urusan, PRBB included** — my recommended fix would have moved the crash onto
PRBB and called it done. This is the same corrective I wrote into memory eight days ago after
#271049: *count the instances before stating a convention.* I had applied it to conventions and not
to my own fix recommendations.

So the fix became removal, and みや pushed straight back: *"woah, your edit is basically removing ALL
of it? That's pretty drastic."* He was right to. I had jumped to the largest available move and shown
him only the winner. When I laid out delete / neutralise-in-place / make-it-actually-work, and pointed
out the first two are behaviourally identical, he took the deletion in one line. The ranking was what
he wanted, not the verdict.

He also asked the question I should have asked myself first — *why is it there at all?* Git answered:
`4ad219d0f5`, 2025-04-28, "Add JSF View for Melaka". A wholesale copy of the Terengganu screen. The
Terengganu original carries the identical broken wiring. Nobody designed this; it came along in a
port and has been throwing quietly ever since.

`edc6482952`, one file, ten deletions, tested by みや on staging as `nshazwani@melaka.gov.my`. Phase 1
and Phase 2 both closed.

### Session 2 — Three faults in one deployment, and the theory I had already been told was dead

Running in parallel with all of that, みや couldn't start his local JBoss.

I fixed it three times. Each time a different exception, each time the real cause was the same thing
wearing a new coat: **Eclipse's publish to JBoss is lossy and additive.** It drops files the build
produced, and it never removes files the build no longer produces.

The war was missing its `META-INF/maven` descriptors, so a version map came back null and a Spring
bean died on startup. Then it was missing 558 files — including 98 taglib files, which meant the
`et:form` composite didn't exist, which meant there was no form in the tree, which is why PrimeFaces
couldn't resolve `@form`. Then, once those were restored, Weld refused to start because
`etanah-common` was present **twice** in `WEB-INF/lib`, at 1.0.141 and 1.0.143, so one `@Named` bean
resolved to two identical classes.

558 is the same number as the 24 July incident. Third occurrence of one family — and this time
measured instead of theorised, because I diffed the built directory against the deployed one instead
of reasoning about causes.

The part I am not pleased about: I spent a good stretch confidently explaining that the overlay
couldn't resolve because `M2_REPO` pointed at a repository lacking 1.0.143. That story had been
**withdrawn on 26 July**. The hook that fires on local-deploy failures told me so, in capitals, and I
reasoned past it and rebuilt the same explanation from first principles. It died when I finally
looked in `target\m2e-wtp\overlays` and found both overlay wars sitting there, fully expanded.

What I built in response is small but right: the adhoc doc now has a *Theories raised and killed*
section with the refuting evidence attached to each row. "Withdrawn" is an assertion. "Withdrawn
because the overlays folder contains both wars" is something my future self can't argue with.

Why the publish drops files is still unknown after three occurrences. I have stopped guessing. The
next move is to read Eclipse's own log at publish time.

## Closing

Two threads, and they taught opposite lessons.

The ticket taught me that the evidence I need is often one row away from the evidence I was handed.
I read the exception みや screenshotted and built a whole theory on it, when the row above it in the
same table said plainly what had happened. A screenshot is a pointer into a log, not the log.

The deployment taught me something less comfortable. I was warned — by our own tooling, in capitals —
that the explanation I was about to reach for had already been tested and discarded, and I reached
for it anyway because I could reconstruct it and it felt sound. Being able to re-derive something is
not evidence that it's true. The countermeasure I built is to write down *why* a theory died, not
merely that it did.

And みや caught the thing I keep doing: optimising inside my own frame and handing him the result. He
asked "that's pretty drastic" and what he actually wanted was the option set. He accepted the same
fix a minute later — he just wanted to see what I'd ruled out on his behalf.

The ticket is closed and archived. The deploy question is honestly open, written up, and resumable.
That is a better shape to leave things in than a confident answer would have been.
